# Open Behaviour page implementation

## Layout

- `app/src/open_behaviour.rs` holds `GET /open-behaviour-items`. It reads `conf/projects.json` and changes a leading `~/` of each project path to the home folder. For each project, it gives one tab with `id`, `name`, `groups`, and `errors`. Each group is one entry of `spec/open-behaviour.json` of the project, with no change.
- `app/src/open_behaviour.rs` also holds `POST /open-behaviour-resolve`. The body has `tab`, `spec`, `id`, and `decision`. `find_item` finds the item in `spec/open-behaviour.json` of the project. The route reads the `origin` remote of the project. It sends `POST https://api.cursor.com/v1/agents`. The key is `CURSOR_API_KEY` from the process environment, or from `.env` at the workspace root when the process value is empty. The only repository is the project. The body has no `customSubagents`. The prompt tells the cloud agent to resolve the item in the project repository and to obey `AGENTS.md` of that repository. The model id is `claude-opus-5-5` with effort `medium`. The route does not wait for the agent. It stores the cloud agent id. It creates `app/data/resolve/<agent id>.log` and reads the run stream in the background. It also writes `app/data/resolve/<agent id>.prompt` with the prompt of the local agent. That prompt gives the project path, the item, and the final decision, and tells the agent to obey `AGENTS.md`. It also writes `app/data/resolve/<agent id>.root` with the project path. A stop of the server does not stop the cloud agent. The stream writes one JSON event on each line. Assistant text becomes an `assistant` event. A tool call with status `running` becomes a `tool_call` event with subtype `started`. A terminal run status becomes a `result` event or an `exit` line. Text that is not JSON stays as a line of the log. `last_run` gives the lines of the log after the last `followup` event, or all lines when the log has no `followup` event. The end checks read only these lines. When the last run has no `result` event, no `exit` line, and the log has no local start line, `GET /open-behaviour-progress` reads the cloud agent and its latest run, and a terminal run adds one end line. `end_cloud_run` handles a terminal run from the stream and from the progress route. For the status `ERROR` in a log with no `followup` event, `start_local` first writes the local start line to the log. Then it starts `cursor-agent --print --output-format stream-json --force --trust --model claude-opus-5-5-medium --workspace <project path>` with the `.prompt` file and the path in the `.root` file, in a new process group. The output of the agent goes to the same log, and an `exit` line follows when the process ends. A lock and the start line in the log let only one local agent start for each chat. When the `.prompt` file or the `.root` file is missing, or the start fails, the log gets the failed end line. A failed start also writes the error text.
- `app/src/open_behaviour.rs` also holds `POST /open-behaviour-followup`. The body has `chat` and `text`. A bad chat id, an empty text, a chat with no log, or a last run with no end returns 400. For a log with no local start line, the route sends `POST https://api.cursor.com/v1/agents/<agent id>/runs` with the text. After a successful send, it writes a `followup` event with the text to the log and reads the stream of the new run in the background. For a log with the local start line, `followup_local` holds the local lock. `local_session` reads the last `session_id` after the local start line. The route writes the `followup` event and starts `cursor-agent` with the same arguments, the `.root` path, `--resume <session id>`, and the text. A failed start writes the error text and a failed `result` event. The route returns the progress of the log.
- `app/src/open_behaviour.rs` also holds `GET /open-behaviour-progress`. `read_progress` reads the log of the chat. Each `assistant` event with text gives a `message` step. Each `tool_call` event with subtype `started` gives a `tool` step with the tool name and the first of these args: `command`, `path`, `pattern`, `globPattern`, `query`, `url`. Each `followup` event gives a `reply` step with its text and sets the status to `running`. Each line that is not JSON gives an `output` step. A `result` event gives the status `finished`, or `failed` and an `output` step with the result text when `is_error` is true. An `exit` line with no `result` event before it gives the status `stopped`. With no `result` event and no `exit` line, the status is `running`.
- `app/web/open-behaviour/context.js` holds the tabs, the saved decisions, the started resolves, the progress, the load, the save, the resolve, and the progress load. It has no DOM code. `state.resolves` maps a decision key to `"starting"` or to the chat id. `"starting"` is not in the DB. `state.progress` maps a decision key to the last loaded progress. `refreshProgress` loads the progress of each started resolve with the status `running` or with no progress. A failed load gives the status `error` with the error text. When a loaded progress has the status `failed`, `refreshProgress` saves the resolves without that key, and keeps the progress. If that save fails, the resolve stays and the page shows the error. `resolve` removes the old progress of the key, so the progress of the new agent loads. One `refreshProgress` runs at a time. `followup` sends the text of a started resolve and keeps the returned progress. Thus, `refreshProgress` loads that progress again. A failed send sets the error and keeps the progress. After each change, it calls the `onChange` function of the page. `decisionKey` gives the key of an item. `groupsByStatus` splits the groups of one tab into open items and decided items. `withKind` gives a tab with only the items of one kind. An empty kind gives the tab with no change.
- `app/web/open-behaviour/index.js` builds the page with the DOM API. It builds the tabs and the cards one time after the load. On each render, it moves each decided card to the bottom of its tab. Thus, an input keeps its text. Text between backticks shows as code. The selected kind is a variable of the page. On each render, the page hides the cards of the other kinds, and places the cards and counts the items with `withKind`. After the load and each 3 seconds, the page calls `refreshProgress`. A card builds its progress steps again only when the status or the number of steps changes. Thus, the scroll of the steps stays when nothing changes. The card text gives the cloud agent id and the URL `https://cursor.com/agents/<agent id>`. It tells the user to turn on the API source filter when the sidebar hides the agent. The follow-up form is in the progress block, after the steps. The page shows it only for a started resolve with the status `finished` or `stopped`. The input clears after a successful send.
- `app/web/open-behaviour/index.css` holds the styles of the page, the tabs, the groups, and the cards.
- The tests are in `app/src/open_behaviour.rs` and `app/web/test/open-behaviour/context.test.js`.

## Persist

- The decisions are the page data `open-behaviour-decisions` in table `page`. Refer to `spec/app/01_server/code-impl.md`.
- The decisions change only after a save is successful.
- The resolves are the page data `open-behaviour-resolves` in table `page`.
- The resolves change only after a save is successful.
- The items are not in the DB.
- The progress is not in the DB. The server reads it from the log on each request.

## Do not

- Do not write a project name or an item of a project in `app/web/`. The page reads those values from the projects.
- Do not change the `id` of a tab, the `spec` path of an entry, or the `id` of an item. The saved decisions and the saved resolves use them in their key.
