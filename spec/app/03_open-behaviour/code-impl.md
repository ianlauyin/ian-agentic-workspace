# Open Behaviour page implementation

## Layout

- `app/src/open_behaviour.rs` holds `GET /open-behaviour-items`. It reads `conf/projects.json` and changes a leading `~/` of each project path to the home folder. For each project, it gives one tab with `id`, `name`, `groups`, and `errors`. Each group is one entry of `spec/open-behaviour.json` of the project, with no change.
- `app/src/open_behaviour.rs` also holds `POST /open-behaviour-resolve`. The body has `tab`, `spec`, `id`, and `decision`. `find_item` finds the item in `spec/open-behaviour.json` of the project. `start_agent` makes the chat id `local-<nanoseconds since 1970>` and creates `app/data/resolve/<chat id>.log`. It writes `app/data/resolve/<chat id>.prompt` with the prompt and `app/data/resolve/<chat id>.root` with the project path. The prompt gives the project, the project path, the file, the spec, the item, and the final decision, and tells the agent to obey `AGENTS.md`. It tells the agent to remove the full item object from the `items` list of its spec entry when the item is resolved, and not to keep it with a resolved status or a note. Then `spawn_local` starts the first agent with the model `claude-sonnet-5-5-medium`. The route does not wait for the agent. When the first agent cannot start, the log gets the error text, and `start_local` starts the Grok agent. When the Grok agent also cannot start, the route returns 500 with the error of the first agent. The server calls no Cursor API.
- `spawn_local` starts `cursor-agent --print --output-format stream-json --force --trust --model <model> --workspace <project path>` with the prompt, in a new process group. The output of the agent goes to the log, and an `exit` line follows when the process ends.
- The two agents share one log. `GROK_START` in the log begins the Grok agent. `last_run` gives the lines of the log after the last `followup` event or `GROK_START` line, or all lines when the log has neither. The end checks read only these lines.
- After the first agent exits, `start_grok_after_fail` runs. When the log has no `followup` event and `local_failed` finds a failed run, it calls `start_local` for the Grok agent. `local_failed` reads the first end of the run: a failed `result` event, or an `exit` line with a code that is not 0 before a `result` event. When the Grok agent cannot start, the log gets a failed `result` event.
- `start_local` holds a lock, writes `GROK_START`, and calls `spawn_local` with the `.prompt` file, the path in the `.root` file, and the model `grok-4.7-high`. The lock and the start line let only one Grok agent start. A missing `.prompt` file or `.root` file, or a failed start, is a failed start. A failed start writes the error text.
- `app/src/open_behaviour.rs` also holds `POST /open-behaviour-followup`. The body has `chat` and `text`. A bad chat id, an empty text, a chat with no log, or a last run with no end returns 400. `followup_local` holds the local lock. `local_session` reads the last `session_id` after `GROK_START`, or in the full log when the Grok agent did not start. The route writes the `followup` event and starts `cursor-agent` with the model of the current agent, the `.root` path, `--resume <session id>`, and the text. A follow-up agent does not start the Grok agent. A failed start writes the error text and a failed `result` event. The route returns the progress of the log.
- `app/src/open_behaviour.rs` also holds `GET /open-behaviour-progress`. `read_progress` reads the log of the chat. Each `assistant` event with text gives a `message` step. Each `tool_call` event with subtype `started` gives a `tool` step with the tool name and the first of these args: `command`, `path`, `pattern`, `globPattern`, `query`, `url`. Each `followup` event gives a `reply` step with its text and sets the status to `running`. Each line that is not JSON gives an `output` step. `GROK_START` also sets the status to `running`. A `result` event gives the status `finished`, or `failed` and an `output` step with the result text when `is_error` is true. An `exit` line with no `result` event before it gives the status `stopped`. For the first agent with no `followup` event, a failed `result` event and an `exit` line with a code that is not 0 keep the status `running`, because the Grok agent starts next. With no `result` event and no `exit` line, the status is `running`.
- `app/web/open-behaviour/context.js` holds the tabs, the saved decisions, the started resolves, the progress, the load, the save, the resolve, and the progress load. It has no DOM code. `state.resolves` maps a decision key to `"starting"` or to the chat id. `"starting"` is not in the DB. `state.progress` maps a decision key to the last loaded progress. `refreshProgress` loads the progress of each started resolve with the status `running` or with no progress. A failed load gives the status `error` with the error text. When a loaded progress has the status `failed`, `refreshProgress` saves the resolves without that key, and keeps the progress. If that save fails, the resolve stays and the page shows the error. `resolve` removes the old progress of the key, so the progress of the new agent loads. One `refreshProgress` runs at a time. `followup` sends the text of a started resolve and keeps the returned progress. Thus, `refreshProgress` loads that progress again. A failed send sets the error and keeps the progress. After each change, it calls the `onChange` function of the page. `decisionKey` gives the key of an item. `groupsByStatus` splits the groups of one tab into open items and decided items. `withKind` gives a tab with only the items of one kind. An empty kind gives the tab with no change.
- `app/web/open-behaviour/index.js` builds the page with the DOM API. It builds the tabs, one section for each group, and the cards one time after the load. Each card is in the section of its group, in the order of the source. A render does not move a card. Thus, an input keeps its text. On each render, the page hides a section with no item of the selected kind. Text between backticks shows as code. The selected kind is a variable of the page. On each render, the page hides the cards of the other kinds, and shows the sections and counts the items with `withKind`. After the load and each 3 seconds, the page calls `refreshProgress`. A card builds its progress steps again only when the status or the number of steps changes. Thus, the scroll of the steps stays when nothing changes. The card text gives the chat id and tells that the local agent works in the project folder. The follow-up form is in the progress block, after the steps. The page shows it only for a started resolve with the status `finished` or `stopped`. The input clears after a successful send.
- `app/web/open-behaviour/index.css` holds the styles of the page, the tabs, the groups, and the cards.
- The tests are in `app/src/open_behaviour.rs` and `app/web/test/open-behaviour/context.test.js`.

## Persist

- The decisions are the page data `open-behaviour-decisions` in table `page`. Refer to `spec/app/01_server/code-impl.md`.
- The decisions change only after a save is successful.
- The resolves are the page data `open-behaviour-resolves` in table `page`.
- The resolves change only after a save is successful.
- The items are not in the DB.
- The progress is not in the DB. The server reads it from the log on each request.

## Do not

- Do not write a project name or an item of a project in `app/web/`. The page reads those values from the projects.
- Do not change the `id` of a tab, the `spec` path of an entry, or the `id` of an item. The saved decisions and the saved resolves use them in their key.
